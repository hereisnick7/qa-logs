# /qa-logs — Log Investigation Agent v1.6

> Скилл + суб-агент для Claude Code. Расследует инцидент по описанию симптома (юзер/сущность + что не так + примерное время) через Grafana/VictoriaLogs — восстанавливает причинную цепочку между сервисами и выдаёт отчёт с конкретной рекомендацией или наводкой, куда копать бэкенд-разработчику. Если логов не хватает для вывода — предлагает эскалацию во второй агент `qa-database` (read-only Postgres, отдельный проект), но сам в БД не ходит.

---

## Что делает

Вместо того чтобы вручную листать Grafana Explore в поисках нужного момента —
агент делает это за пару минут через CLI-запросы к VictoriaLogs.

1. Принимает свободное текстовое описание симптома ИЛИ ключ Jira-задачи
2. Находит нужное временное окно через гистограмму объёма логов (`grafana-hits`), не листая всё подряд
3. Вытаскивает релевантные строки логов (`grafana-logs`), проверяя, что выборка не обрезана лимитом
4. Сортирует события хронологически поперёк всех сервисов/подов — причина обычно видна только на стыке "издатель события" → "потребитель события"
5. Пишет расследование как единую причинную цепочку: каждая строка лога сразу со своим смыслом (`[FACT]` → что это вызывает), не отдельно тайм-лайн и отдельно вывод
6. Помечает уверенность каждого утверждения: `[FACT]` / `[HYPOTHESIS]` / `[UNKNOWN]`
7. Проверяет масштаб: разовый инцидент или повторяющийся паттерн
8. Заканчивает конкретным предложением ("стоит проверить `module:function`") ИЛИ, если данных не хватает, наводкой бэкенд-разработчику куда смотреть — **всегда как гипотеза**, никогда как подтверждённый фикс: у агента нет доступа к репозиторию, только к тому, что видно в самих логах (имена модулей/функций)
9. **Не имеет доступа к БД.** Если после всех шагов остаётся конкретный вопрос, который мог бы закрыть снимок текущего состояния в базе — явно называет его в `## ❓ Вопросы` (`→ **Эскалация:**`) и помечает `escalate_db: yes` в служебном футере отчёта. Сам запрос в БД не делает и агента `qa-database` не запускает — это решение оркестратора/пользователя
10. Только отчёт — тикет в Jira заводится отдельным явным шагом, агент сам этого не делает

## Использование

```
/qa-logs "юзер 42, дублируются записи о проверке, с 6 утра"
/qa-logs DEV-XXXX                                        # Jira-ключ — агент сам читает задачу
/qa-logs DEV-XXXX "уточнение: только для одной геозоны"  # Jira-ключ + доп. контекст
```

---

## Формат отчёта

```
## 🔗 Ход расследования     ← причинная цепочка: каждая строка лога + её смысл
## ИТОГ                     ← самодостаточный вывод, даже без чтения шагов выше
## 📊 Масштаб                ← разовый инцидент или повторяющийся паттерн
## 🔧 Рекомендации           ← конкретное предложение ИЛИ куда копать (гипотеза, не фикс)
## ❓ Вопросы                 ← опционально; включает → Эскалация, если escalate_db: yes
```

## Структура файлов

```
.claude/
  agents/
    qa-logs-agent.md          ← суб-агент (основная логика)
  skills/
    qa-logs/
      SKILL.md                ← скилл /qa-logs (оркестратор), включая хендофф в qa-database
config/
  qa-logs-context.md          ← справочник по сервисам/ID/паттернам (заполни под свой продукт)
modules/
  grafana/
    client.py                 ← HTTP-клиент Grafana API (proxy к VictoriaLogs)
    cli.py                    ← workflow grafana-info / grafana-logs / grafana-hits
  jira/                       ← нужен только для режима "по Jira-ключу"
```

## Установка

### Требования

- [Claude Code](https://claude.ai/code) CLI
- Python 3.9+
- Grafana с датасорсом VictoriaLogs, к которому у тебя есть service account token

### Установка workflow CLI

```bash
git clone https://github.com/hereisnick7/qa-logs.git
cd qa-logs
pip install -e .
```

**Windows:** используй `workflow.cmd` вместо `workflow`.

### Настройка credentials

```bash
mkdir -p config/grafana config/jira
cp config/example/grafana/.env.example config/grafana/.env
cp config/example/jira/.env.example config/jira/.env   # опционально, только для Jira-режима
```

#### Grafana Service Account Token

1. В Grafana: **Administration → Users and access → Service accounts → Add service account**
2. Роль — **Viewer** (агент только читает логи)
3. **Add service account token** → срок действия по вкусу (не "No expiration") → скопируй токен сразу, он показывается один раз

Открой `config/grafana/.env`:
```
GRAFANA_URL=https://grafana.your-company.com
GRAFANA_TOKEN=сюда-вставить-токен
```

Датасорс VictoriaLogs находится автоматически по типу (`victoriametrics-logs-datasource`).
Если у тебя их несколько — задай явно `GRAFANA_LOGS_DATASOURCE_UID` в том же файле.

#### Jira API token (опционально, для `/qa-logs DEV-XXXX`)

1. https://id.atlassian.com/manage-profile/security/api-tokens → **Create API token**
2. Открой `config/jira/.env`:
```
JIRA_URL=https://your-org.atlassian.net
JIRA_EMAIL=you@company.com
JIRA_TOKEN=сюда-вставить-токен
```

### Настройка базы знаний

Открой `config/qa-logs-context.md` и заполни под свой продукт:
- Часовой пояс, в котором ваша админка/Grafana показывает время (см. секцию Timezone)
- Известные сервисы/поды и что они публикуют/потребляют
- Глоссарий доменных ID (правила антифрода, коды событий и т.п.), если такие есть
- Подтверждённые паттерны "это не баг, а вот такой механизм" — по мере накопления опыта расследований

### Эскалация в `qa-database` (опционально)

С v1.6 работа с БД вынесена в отдельный проект —
[qa-database](https://github.com/hereisnick7/qa-database) (собственный README/установка). `qa-logs-agent` сам в базу
не ходит: если логов не хватает, он предлагает конкретный вопрос для
`qa-database`, а решение — запускать его или нет — за пользователем.
Чтобы эскалация реально сработала, `.claude/agents/`/`.claude/skills/` обоих
проектов должны быть видны в одной сессии Claude Code (см. README `qa-database`).
Без него `/qa-logs` работает полностью самостоятельно — просто без этой
эскалации.

### Запуск

```bash
cd qa-logs
claude
```

```
/qa-logs "юзер 42, что-то не так с депозитом, вчера вечером"
```

**Windows:** если команда `workflow` не найдена — используй `workflow.cmd` напрямую.

## История версий

| Версия | Что добавлено |
|---|---|
| v1.0 | Базовое расследование: свободный текст/Jira-ключ → `grafana-hits`+`grafana-logs` → тайм-лайн + Root Cause с метками FACT/HYPOTHESIS/UNKNOWN |
| v1.1 | Найдены и исправлены живым тестированием: VictoriaLogs без сортировки резал `limit` по недетерминированному порядку скана шардов (не по времени) — теперь `client.py` всегда добавляет `\| sort by (_time)`; CLI ломал запросы с кавычками (`"id" AND "keyword"`) |
| v1.2 | Обрезка длинных строк лога — калибровка порога под реальное распределение длин, а не произвольное число; техника `extract`+`keep` для обхода обрезки на конкретном поле |
| v1.3 | Формат отчёта переработан: причинная цепочка (`Ход расследования`) вместо раздельных Таймлайн+Root Cause; добавлен блок `Рекомендации` — конкретное предложение или наводка бэкенду, всегда как гипотеза, никогда как подтверждённый фикс (агент не читает код) |
| v1.4 | Seed Mode убран — агент читает базу знаний (`config/qa-logs-context.md`), но не предлагает в неё правки; это ручной/оркестраторский процесс |
| v1.5 | Добавлен опциональный модуль `db` — read-only cross-check текущего состояния в Postgres прямо внутри `qa-logs-agent` (Step 4b) |
| v1.6 | DB-модуль выделен в отдельного агента — `qa-database` (свой проект, свой README). `qa-logs-agent` больше не ходит в БД сам: вместо Step 4b он лишь помечает `escalate_db: yes` + конкретный вопрос в `## ❓ Вопросы` → `→ **Эскалация:**`, решение о запуске `qa-database` — за пользователем/оркестратором. Также добавлено: расширенный набор ключевых слов по умолчанию для симптомов "расхождение/не сходится" (не дожидаясь второго прохода по запросу пользователя); проверка валюты/единиц перед выводом "выше/ниже порога"; групповое распространение решения на связанные сущности больше не преподносится как отдельный подтверждённый баг без проверки бизнес-правила |
| v1.6 (optimized) | Несколько окружений Grafana (`--account=<name>`, prod/dev — отдельные инстансы; именованный аккаунт никогда не падает обратно на дефолтные ключи); окружение выбирается до первого запроса и не смешивается в одной цепочке; исключение из «hits перед logs» для точного окна инцидента; явная сортировка для запросов с собственным pipe; хендофф бага в `/qa-report --result=bug`; модель — sonnet; сжатие промпта без потери правил |
